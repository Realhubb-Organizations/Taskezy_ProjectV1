Node.js/TypeScript/Express API server, connects directly to `Taskezy_DB` via the least-privilege `taskezy_app` Postgres role. ### Current deployment (as of 2026-08-07)

- Backend: `Taskezy-Server` runs as a Docker container (`taskezy-api`) on an AWS EC2 instance, behind nginx + Let's Encrypt (certbot) for HTTPS, talking to AWS RDS Postgres (`taskezy-db`). Redeploys via SSH + `~/deploy.sh` on the EC2 box (git pull → docker build → swap container → health-check) — **not** automatic on push; a backend change isn't live until that script is run.
- **Deploy ordering hazard**: if a change includes a new DB migration, it must be applied (`psql -f <migration>.sql`) *before* `~/deploy.sh` runs, or every query touching the changed table fails and — because `AppContext.tsx`'s `loadAllRealData()` fetches every domain in one `Promise.all` — the entire app blanks out (properties/leads/users all disappear), not just the affected feature. Hit this for real once (2026-08-07). Worth hardening later (`Promise.allSettled` instead) so one failing domain doesn't zero out the rest.

- Decisions made (and why): CPL uses the ad platform's own `leadsGenerated` count (matches how marketing teams actually report CPL) while Lead Quality/ROI use CRM-tracked `leads` (the source of truth for what actually happened to those leads) — these are two different, legitimate counting systems and the UI labels them separately rather than conflating them. - Known issues / TODO follow-ups: "Total spend on total leads" for managers/agents is a proportional allocation (their leads ÷ total leads in range × total spend), not a true per-lead cost trace — there's no data linking a specific lead to the specific ad dollar that generated it, so exact attribution isn't possible with the current mock data model. `computeROIMultiple` uses lead `dealValue` (property price) as "booking value," not actual brokerage/commission revenue, since commission % isn't tracked on Lead/Invoice yet.
- Next up: if precise revenue-based ROI is wanted, tie ROI to `Invoice.totalAmount` (or a commission field) instead of `dealValue`. If exact spend-to-lead attribution is wanted, `Lead` would need an `adSpendRecordId` (or campaign+date key) set at ingestion time instead of the proportional-allocation approximation.

### 2026-08-07 — Login email lookup made case-insensitive
- What was done: A sales agent couldn't log in with admin-provided credentials ("Invalid email or password"). Investigation found `auth.service.ts`'s login query did a case-sensitive exact match on email (`WHERE email = $1`) — confirmed this specific account wasn't actually affected (her stored email matched exactly what she was typing), but it's a real, separate bug regardless: an account created as "Neha@..." couldn't log in typing "neha@...". Fixed the login query to `WHERE LOWER(email) = LOWER($1)`, and normalized email to lowercase at user-creation time so future accounts are stored consistently. The actual login failure in this case was traced to a password mismatch, resolved by resetting her password through the normal Edit User flow.
- Files touched: `Taskezy-Server/src/modules/auth/auth.service.ts`, `Taskezy-Server/src/modules/users/users.repository.ts`.
- Decisions made (and why): normalized only at creation time (new accounts), not via a backfill migration on existing rows — the case-insensitive login match makes a backfill unnecessary for login purposes; existing mixed-case stored emails are cosmetic only.
